# How do existing agent skills, review prompts and lint tools detect over-thin code (shallow modules, pass-through wrappers, premature abstraction, one-use helpers)?
Answer: Sources converge on a small set of judgement checks (deletion test, "interface about as complex as the body", rule of three, "does the abstraction still fit") plus one mechanical family (delegation-ratio detectors); nobody publishes a validated single-caller or files-per-feature threshold. This repo already covers most judgement checks; the new material is concrete scriptable pre-filters, the "inline back, then re-extract" remedy, and explicit false-positive guards. Confidence: medium.
Versions: n/a. Checked: 2026-11-19.

Source classes: PRIMARY = Ousterhout lecture notes, Fowler/Refactoring.guru, Metz, Muratori, linter docs. SKILL = public agent-skill files read via `gh api`. BLOG = pointers and anecdotes only. No Reddit thread was retrieved; the search returned blogs, HN mirrors and Product Hunt, so Reddit is unrepresented.

## Findings

### A. Primary texts
- Shallow module: interface nearly as complex as what it provides; using it costs about as much as writing the code yourself. Ousterhout prefers a simple interface over a simple implementation. (Ousterhout, Stanford CS190 [lecture archive](https://grin.io/archive/web.stanford.edu~~ouster~cgi-bin~cs190-winter18~lecture.php%3ftopic=modularDesign.html), deep vs shallow). Heuristic: compare interface cost to behaviour hidden. Guard: size is not depth; 200-2000 line classes are fine if the abstraction is powerful (same page, "when small is fine"). Check type: LLM judgement. This is a lecture-note mirror, not the book; page numbers unchecked.
- Pass-through method: a method that does almost nothing but forward args to a similar-signature method; each layer should present a different abstraction. (same lecture; the "similar signature" wording and p.36 cite come from a [search summary of book notes](https://dev.to/markadel/a-philosophy-of-software-design-summary-pk9), secondary). Guard stated in those notes: a dispatcher pass-through can be useful (secondary, same search). Check type: scriptable pre-filter (body is one call, args forwarded unchanged), judgement to confirm.
- Classitis: taking "small classes" to an extreme produces many shallow classes; Ousterhout blames teaching that classes should be small. ([lecture](https://grin.io/archive/web.stanford.edu~~ouster~cgi-bin~cs190-winter18~lecture.php%3ftopic=modularDesign.html), Classitis).
- Middle Man: class mostly delegates; treatment Remove Middle Man. Guard: keep if added on purpose to cut dependencies, or if it is a Proxy/Decorator. ([Refactoring.guru](https://refactoring.guru/smells/middle-man), Signs and When to ignore). Judgement.
- Speculative Generality: an unused class, method, field or parameter; treatment Collapse Hierarchy, Inline Class, Inline Method, Remove Parameter. Guards: framework code whose users need it; check whether unit tests use it before deleting. ([Refactoring.guru](https://refactoring.guru/smells/speculative-generality), When to ignore). Unused-ness is scriptable (grep or AST callers); intent is judgement.
- Lazy Class: a class that does not justify its upkeep, often shrunk by later refactors or built for work that never came; treatment Inline Class. Guard: may be a deliberate placeholder for planned work, balance clarity and simplicity. ([Refactoring.guru](https://refactoring.guru/smells/lazy-class), Signs and When to ignore). Inline Class applies when the class "does almost nothing" and no responsibilities are planned for it ([Refactoring.guru](https://refactoring.guru/inline-class), When to use). Judgement.
- Metz: wrong abstraction costs more than duplication; once an abstraction stops fitting, devs keep patching it with parameters and conditionals. Remedy: inline the abstraction back into each caller, delete what each caller does not use, then re-extract from what remains. Tell-tale: a shared function accreting parameters and conditionals. ([Metz](https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction), recommended procedure; read through a fetch summary, so wording is paraphrase). Judgement; the parameters-and-branches signal is partly scriptable (parameter count, boolean flags, branch count per caller).
- AHA: duplicate first, then read how copies differ; bending a shared function with a new condition per use case marks a wrong abstraction. (Kent C. Dodds, [AHA programming](https://kentcdodds.com/blog/aha-programming), BLOG-grade but a named heuristic.)
- Muratori semantic compression: write the specific case first, wait for a second instance before extracting, then compress duplicated meaning, not lines; "usable before reusable". ([Muratori](https://caseymuratori.com/blog_0015)). Heuristic: no abstraction without two real instances. Judgement. His OOP-first criticism is opinion.
- Fowler YAGNI: only code that adds complexity now for a presumed future need; four costs (build, delay, carry, repair). Not YAGNI: work that makes code easier to change, or prep that adds no complexity. ([Fowler](https://martinfowler.com/bliki/Yagni.html)). Useful as a guard: a seam that is free and clarifying is not a violation.
- Abramov "WET Codebase": the talk page says only that strict dedup can make software unreadable; details not retrievable from the page. ([overreacted](https://overreacted.io/the-wet-codebase/)). Not usable as a source for heuristics.

### B. Agent skills and prompts (SKILL)
- loopkit `simplify`: "premature abstraction: a class/strategy/factory for one caller. Inline it. Abstract on the THIRD use"; "an interface with one implementation, a generic with one type: delete the indirection"; final test: justify every changed line by the request. ([SKILL.md](https://github.com/Archive228/loopkit/blob/HEAD/skills/simplify/SKILL.md)). Heuristic: caller count (1 means inline) and implementation count (1 means no interface). No false-positive guard stated. Caller and implementer counts are scriptable (grep, AST); the verdict is judgement. Note it says third use, Muratori says second; sources disagree.
- mattpocock `improve-codebase-architecture`: friction prompts (understanding one concept needs hopping across many small modules; interface nearly as complex as implementation; pure functions extracted for testability while bugs live in the wiring), deletion test, scope by git hot spots. ([SKILL.md](https://github.com/mattpocock/skills/blob/HEAD/skills/engineering/improve-codebase-architecture/SKILL.md)). LLM judgement; hot-spot scoping is scriptable. The zebbern `deep-module-refactor` copy has the same text ([SKILL.md](https://github.com/zebbern/claude-code-guide/blob/HEAD/skills/deep-module-refactor/SKILL.md)).
- oh-my-claudecode `architecture-survey`: three finding classes (shallow modules, hypothetical seams "crossed by exactly one adapter with no second caller; checkable by counting callers", logic behind the wrong seam); demolition test; "only load-bearing shallowness is a finding"; findings carry severity, confidence (heuristic-class is low by construction) and actionable. ([SKILL.md](https://github.com/Yeachan-Heo/oh-my-claudecode/blob/HEAD/skills/architecture-survey/SKILL.md)). Seam counting is scriptable; the rest judgement.
- luoling8192 `software-design-philosophy-skill` as summarised by a fetch: flags interface as complex as implementation, callers composing several pieces for a common task, adjacent layers with similar abstractions, pass-through variables; guards: size is not complexity, narrow implementation behind a general interface is not automatically a flaw. ([SKILL.md](https://cdn.jsdelivr.net/gh/luoling8192/software-design-philosophy-skill@main/SKILL.md)). Third-party paraphrase of Ousterhout, not independent evidence.
- mjwestcott `ousterhout` skill summary: "Manager"/"Helper" classes that only coordinate, wrappers that rename args but hide nothing, extraction that "just relocates complexity", organisation by execution order, change amplification (edits in many places for one change). ([skill copy](https://www.skills.lc/mjwestcott/dotfiles/mjwestcott-dotfiles-claude-skills-ousterhout-skill-md)). Naming smell (Manager/Helper) is scriptable by grep; rest judgement. Summary came from a fetch model, not a raw read.

### C. Lint and metric tools (scriptable)
- Delegation-ratio middle-man detector: cha-core flags a class with at least 3 methods where at least half only delegate (defaults `min_methods` 3, `delegation_ratio` 0.5). ([cha-core middle_man.rs](https://docs.rs/cha-core/1.7.0/src/cha_core/plugins/middle_man.rs.html)). repotoire counts a method as delegating with exactly one callee and cyclomatic complexity at most 2, flags a class when over 70% delegate. ([repotoire middle_man.rs](https://docs.rs/crate/repotoire/0.3.47/source/src/detectors/middle_man.rs)). Both are small niche Rust tools, so treat the thresholds as examples, not standards. They will flag facades and adapters; the search notes say so only by inference from the heuristic, not from tool docs. Fully scriptable.
- typescript-eslint `no-extraneous-class`: flags classes with no non-static members, constructor-only classes and empty classes; suggests plain functions. Exemption options `allowConstructorOnly`, `allowEmpty`, `allowStaticOnly` (docs "strongly recommend against"), `allowWithDecorator`. ([rule docs](https://typescript-eslint.io/rules/no-extraneous-class)). Scriptable; flags thin classes, not thin functions.
- ESLint `no-useless-constructor`: constructor that only forwards to super. ([ESLint](https://eslint.org/docs/rules/no-useless-constructor)). Scriptable, narrow.
- BLOG pointer: agent-bloat write-ups suggest automated checks (cyclomatic complexity, function length, dead-code analysis, duplication scanners) but "give no numeric values"; guard: keep abstractions where growth is known, the codebase is layered, or cross-cutting concerns (audit, auth) need them. ([agentpatterns.ai](https://agentpatterns.ai/patterns/anti-patterns/abstraction-bloat/)). Another post lists "helper functions used only once" and "two-line helper gets its own module" as common agent output ([Codersera](https://codersera.com/blog/how-to-stop-claude-code-over-engineering-2026/), via a search summary only; the bswen post returned 403 and was not read). Suggested session-end check: `git diff --stat` for new files and utility folders (same search summary). Anecdote, low weight.
- Counterpoint (BLOG/Reddit via search summary, unfetched): a commenter argued file count alone does not show complexity, since modularisation legitimately adds files ([thread](https://lr.us.psf.lt/r/ChatGPTCoding/comments/1l625ca/please_stop_doing_this/mwo564k/?context=3)). Supports not using files-per-feature as a verdict.
- Not found: Sonar, PMD, pylint rules aimed at single-caller functions or trivial wrappers. A pylint `too-few-public-methods` page fetch returned only the nav menu, so its threshold and rationale are unverified. No source gives a validated interface-to-implementation ratio; design-it already rejects that ratio ([design-it SKILL.md](../../skills/design-it/SKILL.md), Measures this vocabulary avoids).

## What this repo already covers vs what is new

Read: `skills/design-it/SKILL.md`, `DEEPENING.md`, `INTERFACES.md`, `skills/deepen-it/SKILL.md`, `skills/review-it/SMELLS.md`, `skills/review-it/SKILL.md`, `skills/it-core/SKILL.md`.

Already covered (inference from the files read):
- Shallow definition and the deletion test (design-it Terms, Principles; deepen-it step 2). Matches Ousterhout, mattpocock and oh-my-claudecode.
- Pass-through and Just-in-case smells, with the deletion test named as the confirmation (SMELLS.md rows 9 and 21). Covers Middle Man and Speculative Generality as judgement hints.
- "One adapter is hypothetical, two are real" (design-it Principles; DEEPENING.md Seams). Covers loopkit "interface with one implementation" and oh-my-claudecode "hypothetical seam".
- Hop-across-small-modules friction, pure helpers extracted for testing, hot-spot scoping by git log (deepen-it steps 1-2).
- Merge safety by dependency kind, and tests moving (DEEPENING.md). Covers the guard "keep seams at I/O and third parties".
- Nothing-unasked-for rule (it-core Reuse before writing rung 1; review-it Spec reviewer flags unrequested shared helpers as Should).
- Hints are never rules, and a documented repo rule switches a smell off (SMELLS.md header; review-it step 3).

New or only thinly covered:
1. Single-caller helper as a named check. SMELLS has no "used once, inline into parent". Source: loopkit simplify, Codersera pointer, Refactoring.guru Inline Method. Detection is scriptable: count call sites per function in the diff or module. Guard needed (see below).
2. Rule of two/three before extracting (Muratori says second instance, loopkit says third, AHA says "a few"). SMELLS "Repeated logic" pushes extraction; nothing says "do not extract a first or second use". Sources disagree on the number.
3. Wrong-abstraction signal and the inline-first remedy: a shared function growing parameters, flags or per-caller branches; remedy is inline into callers, prune, re-extract (Metz, Dodds). Absent in the files read. Partly scriptable (boolean parameters, branch-per-caller).
4. Pass-through variables and adjacent same-level layers (Ousterhout via skill summaries). SMELLS covers pass-through calls only; the "Travelling group" row is related but not the same (values threaded through layers that never use them).
5. Mechanical pre-filter for pass-through: body is a single call, one callee, cyclomatic complexity at most 2, args forwarded unchanged; class with at least half delegating methods. Source: cha-core and repotoire, niche tools. SMELLS is judgement-only today. A script could shortlist candidates for the reviewer.
6. Naming pre-filter: classes or files named Manager, Helper, Util, Wrapper that only coordinate (mjwestcott skill summary). Not in SMELLS.
7. Explicit false-positive guards for thin code. Present partly (deletion test, seams, documented-rule override) but missing the sources' guards: Proxy, Decorator, Facade or dispatcher kept on purpose; framework or public-API surface used by outside callers; tests that call the code (check before deleting); domain-named seams; placeholder for planned work named in a plan or ADR; cross-cutting concerns. Sources: Refactoring.guru (Middle Man, Speculative Generality, Lazy Class), Ousterhout (dispatcher), agentpatterns.ai.
8. Confidence labelling: oh-my-claudecode marks survey findings low-confidence by construction and lets only load-bearing findings through. Review-it already says smells are judgement calls; the per-finding confidence field is new.
9. Diff-shape signals: new files and utility folders per change (`git diff --stat`), new files per behaviour (BLOG only; weak, and the counterpoint above applies).

Suggested check recipe (inference, not from a source): scriptable shortlist (new function with exactly one call site in the diff; single-callee body with forwarded args; interface or abstract class with one implementer; new file under a few dozen lines with one importer), then LLM confirm with the deletion test and the guards in item 7, report as "possible", never Must.

## Open
- No source gives a validated numeric threshold for single-caller helpers, files-per-feature or interface-to-implementation ratio. agentpatterns.ai says to derive thresholds from the codebase baseline; the cha-core and repotoire numbers are unvalidated defaults from small tools.
- Rule of two vs three vs "a few" is unsettled (Muratori, loopkit, Dodds).
- When a one-use helper should be kept for naming or testability: Refactoring.guru (Inline Method) and Ousterhout notes imply "when it hides nothing", but none gives a test beyond the deletion test. design-it's "tests cross the same seam as callers" implies tests should not justify a helper alone; no external source confirms this.
- Reddit and r/ExperiencedDevs opinion was not retrieved; only blog and HN-mirror pointers surfaced, so community disagreement is unmeasured.
- Ousterhout's own text was read via lecture notes and third-party summaries; the book's exact wording and page cites are unchecked.
- Abramov's WET talk content and the bswen post were not retrievable; pylint `too-few-public-methods` rationale unverified; Sonar and PMD coverage not checked.
